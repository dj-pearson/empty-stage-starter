## Codebase Patterns
- Edge functions live in `functions/<function-name>/index.ts` (Supabase Edge Functions use Deno)
- Edge function config goes in `supabase/config.toml` under `[functions.<name>]` with `verify_jwt` setting
- Use `https://deno.land/std@0.168.0/http/server.ts` serve() and `https://esm.sh/@supabase/supabase-js@2` createClient()
- Shared edge function utilities in `functions/_shared/`: cors.ts (CORS headers), auth.ts (JWT verification), url-validator.ts (SSRF prevention)
- All edge functions use `getCorsHeaders(req)` from `../_shared/cors.ts` - no more wildcard CORS
- All privileged edge functions use `authenticateRequest(req)` from `../_shared/auth.ts` for JWT verification
- `functions/sitemap.xml.ts` is a Cloudflare Pages function, NOT a Supabase edge function
- Edge function error responses must return generic messages to clients (`'Internal server error'`), log details server-side with `console.error`
- Always derive user identity from JWT (supabase.auth.getUser()), never trust client-supplied user_id
- Template patterns available in `edge-functions-template/functions/` for reference
- TypeScript check: `npx tsc --noEmit`, Tests: `npx vitest run` (382 passing)
- Test files follow pattern: `src/**/*.test.{ts,tsx}` alongside source files
- Mock Supabase client in tests by mocking `@/integrations/supabase/client`
- Auth page tests need AppProvider wrapper and mocks for: logger.withContext, login-history, use-toast, react-router-dom (useSearchParams), platform
- Schema components: ArticleSchema/FAQSchema/BreadcrumbSchema use Helmet (mock react-helmet-async); RecipeSchema uses useEffect + DOM manipulation (test via document.getElementById)
- US-001 through US-006 already completed strict mode, dead code cleanup, env validation, error boundaries, route error boundaries, and API retry logic
- Build: `npx vite build` (the `npm run build` has an Expo prebuild step that requires native deps; Cloudflare Pages should use `npx vite build`)
- Mobile screens under `app/(tabs)/` use the shared `useNetworkStatus` hook from `app/mobile/hooks/useNetworkStatus.ts` (NetInfo dynamic import, web-safe). Reuse it for any future offline UX.
- Mobile realtime subscription pattern: `supabase.auth.getUser()` inside the effect, build a unique channel name (`mobile-<table>-<userId>`), `.on('postgres_changes', { event:'*', schema:'public', table, filter:'user_id=eq.<id>' }, cb).subscribe()`, clean up via `supabase.removeChannel(channel)` on unmount.
- Soft-delete + 5s undo banner: hide locally, schedule `setTimeout` that commits the supabase.delete, expose Undo to cancel + re-add. If a new delete arrives mid-window, finalise the previous one to prevent stacking banners.
- Cross-platform persistent prefs: `safeStorage` from `src/lib/platform.ts` (web→localStorage, mobile→expo-secure-store). Booleans round-trip as `'true'/'false'`.
- Vite `?raw` imports resolve relative to the importing file. Markdown content lives at `documents/*.md`; before relocating, run `git grep -E '\.md\?raw'`.

    deploy, so the fix had to land in the same change. It is now a KEEP set.
    Second: SHARE_CACHE was declared twice.
  - `window.addEventListener('load', ...)` is wrong the moment registration
    moves later in the boot. A listener added after the load event has fired
    never runs, so the worker would have silently failed to register on
    exactly the fast loads it helps most. pwa.ts now checks
    document.readyState first.
  - In Playwright, `registration.active` is NOT the same as
    `navigator.serviceWorker.controller`. sw.js calls clients.claim() in
    activate and that resolves asynchronously, so a page can have an active
    worker that is not yet intercepting its fetches. Two of the five tests
    failed on this and both looked like source bugs: the share POST reached
    the static server, which answered with the SPA fallback, so the request
    "succeeded" and the cache was empty; and the offline navigation hit
    Chromium's own error page (an empty body) instead of the fallback. Wait
    for the controller whenever the assertion is about interception.
  - A test that polls one half of an async cleanup reads the other half
    mid-flight. unregisterServiceWorkers() removes registrations then deletes
    caches; polling only the registration count saw caches that were about to
    go. One waitForFunction covering both.
  - LATENT, NOT FIXED HERE: cache.addAll(STATIC_ASSETS) in the install handler
    is atomic. All seven assets exist in dist today, but if any one of them
    404s the whole call rejects and NOTHING is cached, including offline.html

    installed and reported healthy. Worth caching them individually.
  - `test-results/.last-run.json` is git-tracked, so any local Playwright run
    dirties the tree. Worth adding test-results/ to .gitignore.

2026-09-09 -- web platform loop, iteration 3. US-823 web half: the grocery list
now survives a shop with no signal. src/lib/webSyncQueue.ts.
================================================================================

- WHAT A SHOPPER GOT BEFORE THIS. Tap an item to check it off in a shop with no
  signal: the row ticks, the server call fails, runOptimisticMutation rolls it
  back, and a toast says it wasn't saved. Every tap. The app has shipped a full
  PWA since US-765 -- service worker, offline.html, installable manifest -- and
  held nothing at all for a failed write.

- THE ONE DECISION THIS TURNS ON. A queued write is the single failure where
  rolling back is WRONG. Every other rollback in this codebase tells the truth:
  the change did not save, so take it off the screen. Rolling back a QUEUED op
  would say "lost" about a change we have just promised to send. So the new
  `offlineQueue` option on runOptimisticMutation, when it returns true, KEEPS
  the optimistic row and toasts "Saved on this device and will sync when you
  reconnect".

  The inverse matters just as much and is where I nearly shipped a bug: if the
  queue could NOT store the op (private window, quota, storage blocked), it must
  return false and get the old rollback. queueWrite therefore does not trust
  enqueue -- offlineQueue.save() deliberately swallows a storage failure so a
  caller's write is not taken down with it, which means "enqueue didn't throw"
  is NOT "the op is stored". It peeks and confirms. A mutation that replaces
  that read with `return true` fails a test.

- QUEUED ONLY FOR THE FAILURES THAT ARE ACTUALLY OFFLINE. The guard is
  isOfflineFailure from iteration 1, so a 403 from RLS is never queued: it would
  replay, fail, replay, and be dropped after five attempts, having told the user
  it was saved the whole time. Mutation-checked -- dropping the guard fails a
  test.

- INSERTS ARE NOT QUEUED, AND THAT IS THE HONEST ANSWER, NOT AN OVERSIGHT.
  groceryRow.ts states that the database owns `id`. A queued insert would
  therefore replay under an id the optimistic row does not carry, arrive back
  over realtime as a SECOND row, and leave a ghost until the next server load.
  The real fix is client-generated ids on insert, which changes the insert
  contract repo-wide. Adding an item offline still fails cleanly with the
  iteration-1 message. Recorded in US-823 rather than half-built.

- THE DEAD STUB IS GONE. OfflineIndicator's queueMutation/clearMutationQueue,
  its QueuedMutation type and the 'eatpal_offline_mutations' key -- three
  declarations with zero callers, found in iteration 1 -- are deleted. The
  "<n> pending changes" badge now reads the real queue, which is the first time
  it can render a number other than zero.

- SCOPED PER USER, by key: 'eatpal.web.syncQueue.<userId>'. Signing in as
  somebody else cannot drain the previous account's writes into the new one's
  household. No shared-key fallback: an op with no owner is an op we cannot
  place, so a signed-out visitor queues nothing at all. Mutation-checked.

- TWO DRAIN TRIGGERS, and the second is the bug iteration 2 found on native:
  the browser 'online' event, and once per mount. A shopper who closed the tab
  in the aisle and opened it at home has no offline->online edge to catch.
  Concurrent drains are refused -- 'online' can fire while a mount drain is in
  flight, and replaying one op twice is two writes for one tap.

- MY TEST INSTRUMENT WAS WRONG BEFORE THE CODE WAS. Two of the first thirteen
  webSyncQueue tests failed, and both were the test's fault: src/test/setup.ts
  replaces global.localStorage with an in-memory mock, so `localStorage.length`
  is a vi.fn (it asserted against [Function spy]) and a spy on
  Storage.prototype.setItem never applies. Fixed by making queueWrite,
  queueWrites and pendingWriteCount take an injectable storage -- which is a
  better seam anyway -- rather than by fighting the global. This is the fourth
  time in this loop that an odd result indicted the instrument, not the subject.

- Measured: 29 tests across the two helper suites, checked against four mutants
  (ignore offlineQueue, queue a server rejection, trust enqueue blindly, drop
  per-user scoping); each is caught. Typecheck ratchet 814 against baseline 814;
  lint 1151 against 1156; check-invisible-chars clean.

- **Learnings for future iterations:**
  - "Did the write succeed" and "did the call throw" are different questions
    whenever the callee swallows errors on purpose. offlineQueue.save() swallows
    by design; trusting it would have shipped rows that look saved forever.
  - Before asserting against a global in this repo, read src/test/setup.ts. Four
    of the globals are replaced with mocks, and a spy on the real prototype is a
    no-op that fails in a way that looks like a product bug.

- WHY IT CROSSES USERS, which is what makes it more than untidy. Cache Storage
  matches on URL. `Authorization` is a request HEADER, and cache.match() ignores

  PostgREST does not send for it. The entry for
  GET /rest/v1/kids?select=* therefore matches ANY user's request for that URL.
  Shared family tablet, which is an ordinary setup for this product: user A
  signs in and loads their children; user B signs in later, loses connection,
  and the worker hands them user A's rows.

  CACHE_NAME carries the build id, so a deploy that changes asset hashes clears
  it. Between deploys it persists, and a deploy that does not change the hashes
  keeps the name and everything in it.

- FIXED: authenticated endpoints go through networkOnlyForPrivateApi, which
  fetches and keeps nothing. Nothing is lost by that -- the app already keeps a
  per-user offline copy in localStorage via AppContext, and CLAUDE.md's load
  precedence treats the server as authoritative anyway. Activation also purges
  entries an older worker left behind, because changing the strategy does not
  remove what is already on disk.

- TESTED BY RUNNING THE SHIPPED FILE, not by reading it. public/sw.js is a
  browser artefact outside the bundle, so the test evaluates it in a vm with
  stubbed service-worker globals and drives its real fetch and activate
  handlers. A source-guard test would have passed on a file that had stopped
  doing the thing.

- ONE ASSERTION EXISTS ONLY TO STOP THE SUITE PASSING VACUOUSLY: a static asset
  must STILL be cached. Without it, a worker that cached nothing at all would

- A NEGATIVE THAT COST TWENTY MINUTES, and the instrument was the problem again.

  their own browser whatever bucket they were in. That is the one browser in
  which a staged rollout gets eyeballed, and "I turned it on at 5% and I can
  see it" is exactly the wrong conclusion to be able to draw. The dashboard
  evicts now: same immediate refresh, no claim it is not in a position to make.

      accident. The new case feeds it a payload with NO version but with
      modern-looking `{ value, at }` entries -- which would be read happily
      without the check.
  (b) Nothing stopped the dashboard writing a value again. The rule is about
      the admin surface, so it is asserted on the import line: the dashboard
      may import evictFlag and must not import writeFlag/writeFlags.

- THE SHAPE CHANGE BROKE TWO TESTS, CORRECTLY. AppContext.precedence and
  InventoryContext.append enabled the ledger flags by hand-writing

- Measured: 3466 tests pass (232 files, 1 skipped). Typecheck 814 against

- **Learnings for future iterations:**
  - Generalising last iteration's find into a sweep is tempting and was wrong.

  - When a mutant survives, ask whether the code it targets was ever load-

2026-09-10 -- web platform loop (new run), iteration 13. US-848: every offline
navigation hit a dead end the cache could have answered. public/sw.js
================================================================================

- A FALSE START, AND IT IS THE MOST USEFUL PART OF THIS ENTRY. My first probe
  said the offline path worked: the worker registered, precached 37 entries
  including /offline.html, an offline navigation to /faq returned the offline
  page, and a subsequent navigation to / BOOTED THE APP with 70 JS/CSS chunks
  cached. I nearly wrote that up as a clean negative.

  It was contaminated. I had reused one browser context across probes, so state
  from an earlier navigation made a route look cached that was not. Three
  isolated trials, fresh context each, said the opposite and said it
  consistently:

      online at /  -> offline /pricing  -> offline page
      online at /  -> offline /         -> offline page   <- the page you are ON
      online at /faq -> offline /pricing -> offline page

- THE DEFECT. networkFirstWithOfflineFallback went straight to offline.html and
  never read the cache. Not the shell precached at install. Not the 70 chunks.
  Not the navigation responses the same function stores on its success path TWO
  LINES ABOVE. Everything needed to serve the app was there and none of it was
  consulted.

- WHICH MADE THE OFFLINE PAGE'S OWN COPY FALSE:

      "Don't worry! TryEatPal works offline. Here's what you can still do:
       View your saved meal plans / Check your grocery list"

  From a dead-end static page you can do neither. The claim was true of the
  cache and false of the page the user was actually looking at.

- FIXED IN THE ORDER THAT MATCHES WHAT THE USER ASKED FOR: the exact cached
  page first (it may be a prerendered route with its own content), then the app
  shell so client-side routing renders whatever they asked for, then the static
  page. All three trials boot the app now, and AppContext hydrates from
  localStorage exactly as the load-precedence contract in CLAUDE.md describes.

- NOT "ALWAYS SERVE THE SHELL". With nothing cached the static page is exactly
  right, and the test that pins that is what stops the shell case passing
  vacuously. The mutant that always serves a shell fails it.

- THE TEST DOUBLE WAS WRONG, WHICH LOOKED LIKE THE CODE BEING WRONG. Three
  cases failed on the first run. The fake Cache API compared raw strings, so
  `cache.match('/index.html')` missed a store keyed by absolute URL -- the real
  Cache API resolves a relative path against the worker's scope. Keys go
  through `new URL(x, scope)` now. Second time this loop a passing
  implementation looked broken because the double disagreed with the platform
  (US-835's storage mock exposed `length` as a function).

- Measured: 3515 tests pass (235 files, 1 skipped). Typecheck 813 against
  baseline 813; lint 1144 against 1144; invisible chars clean. Four mutants,
  four caught.

- **Learnings for future iterations:**
  - One browser context across probes is one shared cache, one shared origin
    and one shared worker. If a result depends on what you did before it, you
    are measuring your own script. Fresh context per trial, and run the trials
    in more than one order.
  - Be most suspicious of a probe that says everything is fine. The clean
    negative is the cheapest possible outcome and therefore the one worth
    re-running before you write it down.
  - A cache you write and never read is not a cache. The success path here had
    been diligently storing navigations for as long as the worker has existed.
  - When a test double and the implementation disagree, check which one models
    the platform. Twice now the double was the liar.

2026-09-10 -- web platform loop (new run), iteration 14. US-849: five prerendered
pages skipped h1 -> h3. src/lib/headingOutline.test.ts
================================================================================

- THE INSTRUMENT NEARLY HANDED ME A MUCH BIGGER, ENTIRELY FALSE FINDING. My
  first scan of the built HTML reported TWO h1 elements on every one of the 29
  pages, the second identical site-wide:

      "EatPal - Meal Planning for Picky Eaters & ARFID"

  A boilerplate h1 duplicated across the whole site would be a serious SEO and
  a11y defect, and it was three sentences from being written up as one. It sits
  inside index.html's <noscript> block. Never rendered when scripts run, never
  in the accessibility tree, not part of the outline. Excluding <noscript> took

- THE REAL FINDING, and it is modest by comparison: /faq, /contact, /guides,
  /meal-plan and /budget-calculator go from the page h1 straight to h3.
  Jumping between headings is how many screen-reader users move through a page,
  so a skipped level makes the outline they are walking wrong. VPAT 1.3.1 says
  "Supports -- Semantic HTML, ARIA landmarks, proper heading hierarchy ...
  throughout". Fourth false VPAT row this loop.

- TWO CAUSES. The footer's five column titles were h3 with no h2 anywhere above
  them -- and on /guides that IS the entire outline, because the page's own
  content has no sub-headings at all. And the feature cards on the two
  generator pages were h3. Both are page code; both became h2.

- IN SEVEN FILES, because Footer.tsx's markup is pasted verbatim into
  Accessibility, BlogPost, Contact, TermsOfService, PrivacyPolicy and FAQ. 23
  copies of one heading line. Not this story's job to de-duplicate, so the gate
  instead asserts that none of the six copies drifts back to h3 -- whichever
  one did would reintroduce the jump on its own page and nowhere else.

- THE LAST TWO PAGES BELONG TO SHADCN. /faq opens with AccordionTrigger and
  /contact with CardTitle, both of which render h3 from src/components/ui/,
  which CLAUDE.md puts off limits. So the missing level is supplied from page
  code as an sr-only h2. Deliberately not visible: correcting a heading level is
  not a reason to add copy to a page nobody asked me to redesign.

- Measured: 29 pages, 0 with issues, from 5. 3525 tests pass (236 files, 1
  skipped). Typecheck 813 against baseline 813; lint 1144 against 1144;
  invisible chars clean. Three mutants, three caught -- two of them requiring a
  full rebuild, since the gate reads dist/.

- NEGATIVES, and the manifest one is a genuinely clean bill of health. All five
  PWA icons exist and match their declared sizes; 192 and 512 are present with
  "any maskable"; name, short_name, start_url, scope and display standalone are
  all set. share_target declares a multipart POST to /share, and the worker
  really does implement it -- with an unversioned cache that deliberately
  survives activation so a pending share is not thrown away -- and
  tests/pwa-offline.spec.ts already drives it end to end. One dead declaration
  recorded rather than fixed: protocol_handlers registers web+eatpal ->
  /import?url=%s, there is no /import route, and nothing in the repo emits such

- **Learnings for future iterations:**
  - The bigger the finding, the harder to check it before believing it. "Every
    page has a duplicate boilerplate h1" was exciting, tidy and wrong, and the
    only thing between it and the commit message was asking where the second
    one came from.
  - <noscript> is markup that is never rendered. Any scan of built HTML that
    reasons about what a user or a screen reader sees has to strip it, the same
    way code scans strip comments.
  - When a component you may not edit owns the wrong heading level, add the
    level above it rather than fighting the component. sr-only is the honest
    way to fix structure without redesigning.
  - A gate that reads dist/ needs a full rebuild per mutant. Worth it, and
    worth saying so: it is why this iteration has three mutants and not six.

2026-09-10 -- web platform loop (new run), iteration 15 (LAST). US-850: the
manifest registered a protocol handler with no route behind it.
src/lib/manifestRoutes.test.ts
================================================================================

- TWO NEGATIVES FIRST, both measured rather than assumed, and both closing out
  VPAT rows. FOCUS VISIBILITY (2.4.7): tabbed through /, /pricing and /faq --
  132 stops -- and every single one has an outline or a box-shadow ring. Zero
  failures. FOCUS ORDER (2.4.3): measured the y-position of every stop and
  looked for backward jumps. There are some, and all of them are correct:
  multi-column footers go down one column and back up to the top of the next,
  which is the expected pattern, and the cookie banner deliberately precedes
  the header. The accessibility widget's floating trigger is the 5th tab stop
  while sitting at the bottom-left of the screen -- a mild ordering wart, not a
  violation, and recorded rather than changed.

- THE FIND. public/manifest.json declared

      { "protocol": "web+eatpal", "url": "/import?url=%s" }

  There is no /import route in App.tsx and nothing in the repo emits a
  web+eatpal: link. An installed PWA registers that handler WITH THE OPERATING
  SYSTEM, so the app advertised a capability it does not have; anything that
  ever followed such a link would land on the 404 page.

- REMOVED, NOT IMPLEMENTED. You do not ship a handler for a protocol you do not
  handle, and inventing an /import route to satisfy a declaration nobody uses
  would be building a feature to justify a typo. The manifest carries a note
  saying to re-add it in the same change that adds the route.

- THE MANIFEST IS THE ONE FILE THAT HANDS URLS TO THE OS instead of to the
  router, which is why nothing noticed. The gate checks all of them -- start_url,
  the four shortcuts, share_target.action and any protocol handler -- so the
  next one to drift fails with the same assertion.

- INSTRUMENT BUG, and it is the same shape as most of the others this loop: the
  first route resolver kept nested routes as a flat set of NAMES, so
  "/pricing/planner" resolved -- /pricing is a route and "planner" is a route
  name somewhere under /dashboard. Nested paths are attributed to the nearest
  absolute path declared before them now. The mutant that flattens it again
  fails four tests.

LOOP CLOSED -- 15 iterations, US-835 to US-850
================================================================================

- SIXTEEN STORIES, fifteen closed and one deliberately left open (US-847, the
  WebP og:image, which needs an asset and an owner's decision rather than code).

- WHAT THE FINDS HAD IN COMMON, in rough order of how often it came up:

  1. A CONFIDENT COMMENT IS A TEST THAT NEVER RUNS. Five of the fifteen were
     written down, in the file that had them, by someone who knew: the VPAT
     four times over (2.4.1, 2.1.2, 2.2.2, 1.3.1), docs/entitlements.md's "no
     gate exists at the invite path", resetConsent's "a reload applies the new
     state", and _headers' "the built index.html carries zero inline <script>".
     The prose was right about the mechanism and nobody had checked it lately.

  2. HALF-WIRED DECISIONS. Somebody designed the whole thing and left one wire
     off: onConsentChange with no subscribers, a limit table with no gate, an
     unsubscribe that two of three senders honoured, a cache written and never
     read, a deferral that deferred the call but not the download.

  3. THE INSTRUMENT WAS WRONG BEFORE THE CODE WAS, about ten times. Comments
     quoted as code (three separate iterations), `[^>]*` as an attribute list
     (79% under-report), one timestamp read out of three, substring matching on
     a class name, a flat set of route names, and a <noscript> h1 counted as a
     real one -- that last would have been a big and entirely false finding.

  4. TEST DOUBLES THAT DISAGREED WITH THE PLATFORM, twice, and both times a
     correct implementation looked broken: a storage mock exposing `length` as
     a function, and a Cache API double comparing raw strings where the real one
     resolves relative URLs.

  5. BUILD IT AND RUN IT. Nine iterations of reading found nine real defects.
     Then one build found 126 kB of Sentry blocking first render, and a browser
     under the production CSP found a refused theme script on every page, a
     19px overflow on the page that takes the money, and an offline path that
     ignored its own cache. Some defects have no textual tell at all.

- MEASURED AT CLOSE: 3539 tests pass (238 files, 3 skipped), up from 3405.
  Typecheck 813 against a baseline lowered from 814. Lint 1144, lowered from
  1148. Eager bundle 266.6 kB gz against a budget lowered from 454 to 280 --
  129 kB less than the loop started with. Bundle total 2396/2510 kB. Supabase
  config 33/33. Invisible chars clean. 71 mutants across the fifteen
  iterations, every one caught, four of them only after the test that missed
  them was rewritten.

- **The one thing worth carrying forward:** every iteration that produced a
  real find started by measuring something, and every iteration that nearly
  produced a false one started by believing a sweep. Assert the instrument
  first -- a floor, a control, a known-bad input -- and check the first three
  hits by hand before building anything on the list.
